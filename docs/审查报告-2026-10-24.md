## P1-1 封面泵回写与扫描提交段 lost-update

**位置**：`LocalMediaSource.kt:451-457`（applyCovers）与 `:810`（commitGate 提交段）。

applyCovers 是无锁三步 read-modify-write：`current = _media.value` → map 合并封面 → `_media.value = merged`。扫描提交段 `_media.value = items` 只受 `commitGate` 的代际锁保护，**泵的回写不走这道门**。两线程（泵 io 线程 / 扫描 io 线程）真正并行时，若泵在提交前读了 current、提交后写回 merged，就把旧列表整份覆盖掉刚提交的新列表——本轮扫描的增删、AVI 时长补读全部回退，直到下次扫描。

讽刺点：代码注释自己写着「泵写入与扫描提交可能并发，整表替换会用旧列表覆盖掉新一轮扫描的结果」——merge 只保住了封面不丢，**没有解决新 items 被覆盖的问题**，开发者已知并发存在但缓解措施不完整。

触发概率：applyCovers 每 250ms 一次、易损窗口是 map 那一下（大库约百微秒~毫秒级），提交只在扫描收尾发生一次。窗口窄但后果严重（数据回退）。首扫场景 publish 早于提交、泵全程在跑，两时间线天然重叠。

**修复方向**：applyCovers 的 RMW 套进 commitGate（或代际检查：读 current 前取 generation、写回前 `commitIfCurrent` 不成立则丢弃这批封面回写，下轮 publish 自然重放）。

## P1-2 SAF children 游标 null 被固化为「空目录」

**位置**：`LocalMediaSource.kt:1771`（`query(childrenUri, …)?.use { … }`）。

provider 对 children URI 返回 null（契约允许，如瞬时不可用）时，`?.use` 整段静默跳过：不进 onFailure、`partial` 保持 false、`childDirs == 0`。后果链：① 该目录隐藏媒体本轮全漏；② `completeWalk` 判 `warnings.isEmpty()` 通过 → **空叶子写进 ScanWalkIndex 并落盘**；③ `complete = incompleteReasons.isEmpty()` → 快照被替换、孤儿清理照跑——**该目录文件的播放历史/收藏被当孤儿清掉**（数据丢失）；④ 父目录 mtime 未变 → TTL 5 分钟内 `reusable` 命中，继续漏。

对照：同文件 `:1425` 的 queryScope 对 null cursor 专门记 warning（R0/REV-01 的防御），SAF 分支漏掉了同一防御。**这是数据安全问题，修复优先级应排本报告第一**。

**修复方向**：null cursor 与 query 抛异常同判（partial=true + WARN），并补一条「null 游标不得记索引」的单测。

## P1-3 热切媒体 + 重试 → MediaCodec.flush after Released（真机崩溃）

**现象**（真机 60dd2f94 已复现）：播放中经深链热切另一媒体出错，点错误面板「重试」→ `IllegalStateException: flush() is valid only at Executing states; currently at Released state` → `PlaybackState ERROR "Unexpected runtime error"`。同文件冷启正常。

**根因链**（R8 mapping + media3 1.11.1 源码交叉验证；崩溃帧 = `MediaCodecRenderer.onPositionReset → flushOrReinitializeCodec → AsynchronousMediaCodecAdapter.flush → MediaCodec.flush`）：

1. 重试按钮（`PlayerScreen.kt:3077-3118`）单媒体分支：`prepare(uri)` 后**同步紧跟** `seekTo(resumeMs)` + `play()`。
2. `ExoVideoPlayer.prepare`（:873-887）进入异步探测窗口，期间 `seekTo`（:1906-1914）在 loadPending 时虽记了 pendingSeek，但仍**无条件** `activeController?.seekTo(target)`——这记 seek 立刻打到刚因错误清理（codec 已 release）的会话播放器上。
3. 探测通过后 `applyQueue/applyMedia` 的 `setMediaItems+prepare` 触发 renderer.resetPosition → onPositionReset → 对已释放的异步适配器 flush → 崩。
4. 属 media3 1.11.x 已知缺陷族（androidx/media #2239、#2792、#1489：异步适配器 release 后 flush 无保护）；应用侧的「错误后立即再喂 seek/prepare」是最典型触发姿势。冷启不复现是因为全新播放器不存在「半途而废的错误清理状态」。

次候选：`onSurfaceSizeChanged` 在 READY+暂停时自动 `seekTo(currentPosition)`（ExoVideoPlayer.kt:481-488）同样能触发同型 flush；三候选：擦洗模式挂起 seek 的打断式落地。

**修复方向**（应用侧能做的）：① loadPending 窗口不向 controller 转发 seekTo（只留 pendingSeek）；② onSurfaceSizeChanged 自动 seek 加「非错误态」保护；③ 评估 media3 升级到修过 async adapter 生命周期竞态的版本。

## P2-4 requestCovers 插队对已入队 id 空操作

`CoverPump.request`（:190-205）里 `if (knownIds.add(id))` 是插队前置条件——只有**本轮从未登记**的 id 才 addFirst。而每次扫描提交都 `publish(items)` 把全部缺封面条目登记进 knownIds，此后 UI 的 requestCovers 命中的 id 几乎全在集合里：不插队也不重排。E203-C「扫描刚结束、用户滚动库页、可见条目优先」的立身场景**恰好全部踩空**。类里现成的 `queuedIds`（出队即删）本可区分「还在队列」与「已处理」，从未被用于重排。缓解：列表头部恰在队首 + Coil 现场抽帧兜底，表现为「预热经常不生效」而非「封面出不来」。**修复方向**：request 对 `id in queuedIds` 的条目做真正的重排（从队列摘出再 addFirst）。

## P2-5 debounce 吞掉急滚期封面需求

`CoverWindow.kt:249`：`snapshotFlow { sample() }.debounce(150ms)`。kotlinx 的 debounce 语义是「静默 150ms 才发」——急滚期首可见槽位每几帧变一次，计时器被无限重置，**整段 fling 一次请求都发不出去**；首次下发必然发生在滚动停止之后，此时方向判回 IDLE、窗口收窄 ±1 屏。结果 `COVER_FAST_SCROLL_SCREENS = 2` 的扩窗与 FORWARD/BACKWARD 分支只在「慢拖停顿」时偶发生效，与注释「采样间隔通常是一帧」的设计前提自相矛盾。**修复方向**：debounce 改 sample/timeGap 类节流（周期采样 + 尾部补发）。

## P2-6 / P2-7 主线程 IO 与持锁写盘

- **P2-6**：`requestCovers` 调用链（CoverWindow LaunchedEffect 主线程 → CoverPump.request → `ScanTrace.log`）在调用线程同步执行 `File.length()+FileOutputStream 追加`，还要与扫描工作线程的 trace 写争同一把 `synchronized`——主线程可阻塞到别人的写盘完成。违反 `MediaSourceProvider.kt:60`「不阻塞、不在调用线程做 IO」的显式契约。修复：ScanTrace 内部改后台单线程队列（Channel + 写协程），调用侧只入队。
- **P2-7**：`ScanCoverNegativeCache.markFailed` 在 `synchronized(lock)` 内调 `save()→writeBlocking()`（全量 JSON + tmp + move），泵的全部 worker 与 `needsCover` 查表都串到这把锁上；且 `lastWriteAtMs` 只在写成功路径更新——磁盘满/只读时**每个失败项一次不受节流的全量写尝试**，正好发生在最脆弱的故障场景。修复：落盘移出锁（copy-on-write 快照后无锁序列化），写失败也要推进节流时间戳。

## P3 组（简述）

- **#8 泵内 tuner 恒 no-op**：`startPermits` 与 `cap` 用同一表达式（`if (scanning) scanningPermits() else workers`），起点恒等于上限，tuner 从未真正爬坡；`raiseToFull` 直接操作 limiter 后 tuner.permits 脱钩，`summaryLine` 打的 `permits=` 是旧值——**真机取证口径失真**（E203 文档里「泵 6.9ms/项」的调参叙述建立在这个失真读数上，结论本身不受影响但数字来源要打问号）。无功能危害。
- **#9** `latest`（ConcurrentHashMap）publish 只 put、cancel/close 都不清，随「历史见过 id 总数」单调涨；幅度受库规模约束，属无界结构。
- **#10** removeScanFolder 清空路径没 `coverPump.cancel()`：若此刻泵有回写，排空后把**空列表**落成新快照——`snapshotFile.delete()` 被撤销，下次冷启得到 `hasSnapshot=true` 的空库（UI 判「确实空」而非「还没扫」）。
- **#11** 两处持久化 `readBytes()` 全量读入后才比对字节上限（对照 ScanWalkIndex 的正确姿势：先 length 预检、流式复核）；被外部写坏成大文件时先做一次无谓大分配。
- **#12** `ScanCoverNegativeCache.clear()` 无调用点：KDoc 声称「用户清缓存/重置索引 → clear()」，实际 CacheProvider 只删 thumbsDir。坏文件失败结论带 7 天 TTL 存活过用户显式清缓存。是否算缺陷取决于产品意图，建议接入清缓存入口。
- **#13** ScanProgressAggregate 多来源时 total 只含「有 total 的来源」、processed 却是全体之和，可出现「已处理 650/500」；当前仓库只有一个 MediaSourceProvider 实现，属潜伏缺陷——且现有单测把这个混口径当预期锁死了，修时要连测试一起改。
- **#14**（存疑）monitor 协程收尾对 synchronizedList 的 `forEach` 未持其监视锁，与 `onPermitsChanged` 里的并发 add 有 CME 窗口（在 finally 抛出还会吞原始异常）；窗口极窄。
- **#15** `nativeSendDirect` 用 `GetDirectBufferAddress` 取基址，**不看 ByteBuffer.position**——语义上依赖「media3 在 queueInputBuffer 前 buffer 已 flip（position=0）」的隐含契约（旧 ByteArray 路径的 `data.get(it)` 是尊重 position 的）。真机 WMV2 出画正常证明当前 position==0，但契约脆弱：任何上游改变写缓冲方式就会解码错数据而不报错。建议防御：`data.position() != 0` 时走 scratch 复制路径。
- **#16**（存疑）SeekableLocalDataSource 的 read 在锁外做，与空闲回收任务存在理论竞态，ClosedChannelException 被映射成 EOF（语义=截断）而非 IO 错误；media3 单装载线程下不可达，防御性备注即可。
