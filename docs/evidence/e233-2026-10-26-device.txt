  - 读数：`deleteMediaItem` 在 API 30+ 且无 all-files 且属主非本应用时**提前返回 false**
    （注释：MediaProvider 对被删的非本应用媒体必然再弹系统同意框，SAF `deleteDocument`
    也会被其接管），随即只出现应用风格卡「删除失败 / 取消 / 去开启」；
    文件保持、无任何 `Allow None Player to delete this video?` 系统框。

E. 附：隐藏目录 walk 复核（为 E231 观察项取证）
  - 模拟器建 `/sdcard/Movies/.e233-hidden/secret.mp4` → 应用内「重新扫描」→
    `ScanTrace: hidden walk done dirs=1 entries=0 …`（与真机 E231 同读数）；
  - 读码定位：`shouldDescendDirectory(name, inheritedHidden)` 对普通授权根下的
    `.xxx/` 返回 false（E198 裁定「隐藏目录仅用户显式选择时遍历」），
    `treeRootEntersHiddenPath` 才放行"整支显式选中"；
  - 结论：E231 的 `entries=0` 是设计口径而非 walk 缺陷；`queryHiddenDocuments`
    注释中"目录一律下钻"的旧表述已订正。隐藏根显式授权（→ 隐藏项 saf- 删除）
    未复测（SAF 选择器隐藏目录入口未走通）。

边界：
  - 程序集为无 all-files 时**有意不发起**删除（否则系统同意框必然出现，违背 E232
    "只保留应用一层确认"的裁定）；代价是必须先授权才能删，授权后全程无系统框；
  - `saf-`（隐藏目录）文档删除路径未单独复测（MediaProvider 不索引该目录，
    按理论无同意框）；
  - API 26–29 未实测（本批设备 API 36；权限口径以 `MediaAccessTest` 钉住）。
教训（供后续代理）：模拟器 `install -r` 对签名不符会**失败但输出可能被管道吞**，
先用 `dumpsys package | grep lastUpdateTime` 核对实际是否更新，再据旧包行为下结论；
本轮首测的"系统框来自 SAF 删除"实为 10-22 旧包 createDeleteRequest。
