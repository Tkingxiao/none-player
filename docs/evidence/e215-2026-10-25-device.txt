E215 弹幕 TextWidthCache 键=文本+字号 真机证据（60dd2f94，2026-10-25）
================================================================

设备 60dd2f94（小米平板 6，MIUI/API 34）。安装 release（最终构建）：
adb -s 60dd2f94 install -r "None Player/app/build/outputs/apk/release/app-release.apk"

----------------------------------------------------------------
1. 改动
----------------------------------------------------------------
- `TextWidthCache` 从「按字号分代（字号一变整体失效重算）」改为
  **键 = (文本, 字号)**：字号分桶（LinkedHashMap accessOrder LRU，至多 4 桶），
  桶内 文本→宽度，每桶至多 1024 条、超限清桶，总条目上限 = 4 × 1024 = 4096
  （与任务「上限 4096」一致）。
- 旧行为的退化场景：源文件带字号档（B 站 XML fontsize → Danmaku.fontScale，
  ASS Fontsize 同理）时档位交替，分代 clear 让缓存退化为"不缓存"；分桶后
  各档共存。交替抖动（>4 档）的最坏情形等同旧行为，无回归面。
- measure 的 paint 字号设置收进构造 lambda（缓存本体不依赖 android.graphics），
  `TextWidthCache` 从 private 收成 internal 供 JVM 单测；
  `TextWidthCacheTest` 5 项：命中不重测 / 同文本跨字号独立不串值 /
  字号档交替仍命中（旧分代的退化场景钉死）/ 桶 LRU 逐出 / 溢出只清本桶。

3. 真机现象（screenshots/e215-2026-10-25/）
----------------------------------------------------------------
夹具：B 站 XML（`<d p="time,mode,fontsize,color">文本</d>`），fontsize 25/50
两档交替 → Danmaku.fontScale 两档 → 渲染期 textPx 两个值（多桶路径）。

- 隔离验证：给 np-h264.mp4（6s 彩条短片、无同名字幕）配同名
  `np-h264.xml`（0–5.5s 每 0.5s 一条，25/50 两档交替，橙色）。
  深链起播 ~4s 截图 `danmaku-nph264.png`：**两档字号同屏、各占车道、
  左移滚动**——「E215宽度缓存02号字25」（小号）与「01号字50」（大号）
  同时在屏。旧分代实现在这个内容上每帧都在整表失效重算（fontSize 交替），
  分桶后两档宽度都命中缓存（渲染值不变，路径由单测钉住）。
- 过程记录（不计证据）：`1080p官方中字.mp4`（2:22:03 QA 合集）配 360 条
  夹具（每 10s 一条）未能在截图窗口内目视确认——同目录同名 `.ass` 是字幕
  压测文件（「cue#N 高频字幕测试」，同一屏几十条字幕 cue 同时渲染），
  弹幕文本被字幕洪水淹没，截图时机也未落进 10s 间隔的可见窗；该组截图
  （danmaku-render*.png）保留作过程参考，不作为本批证据。
- 弹幕同目录自动匹配依赖「所有文件访问」（MANAGE_EXTERNAL_STORAGE），
  真机以 `appops set ... allow` 授权后验证，测毕已恢复 default。
- logcat 无 FATAL / AndroidRuntime 异常。
