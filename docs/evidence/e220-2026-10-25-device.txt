E220 历史单条删除 + 批量清空 真机证据（emulator Pixel_Tablet，2026-10-25）
================================================================

设备：Pixel_Tablet 模拟器（2560x1600/Android 15，主验证机）——手机
（Redmi rothko）的 USB 在宿主重启后断开未重连。应用为当前 release
（E220 完整构建）。注意：模拟器上的旧包是 10-14 签名，卸载重装（QA 数据
可弃）；SAF 目录重新授权 Movies；历史记录用 np-e220.mp4（30s 夹具，
_id=1000000047/49 两条深链各播 ~12s 造出）。

----------------------------------------------------------------
1. 改动
----------------------------------------------------------------
- **HistoryStore.HistoryDao**：新增 `@Transaction deleteReturning(key)`——
  读整行 + 删除一个事务（否则「读到行 → 别处更新进度 → 删掉新行」会把
  较新断点连同旧快照一起冲掉）。
- **HistoryRepository**：`removeHistory(key)`（行不存在返回 false，双击/
  并发第二次调用是正常路径）与 `undoRemoveHistory(key)`。撤销留底在仓库
  内部内存表（`lastRemovedForUndo`，键 → 被删整行）——实体类型不出本模块
  （internal），留底只能放这里；进程死则留底丢（toast 窗口内语义足够）。
- **core/ui NpToast**：`show(text, actionLabel, onAction)` 动作扩展
  （向后兼容：纯文本 show 清掉动作）；Host 同胶囊渲染动作钮（accent 色，
  点击即回调并清 toast）。
- **ProfileScreen**：播放历史子页——
  * 长按卡片 = 移除该条（`NpMediaCard.onLongClick` 既有通道透传；收藏页
    不注册长按）；
  * 反馈 = `已从播放历史移除` toast + 「撤销」动作（undo 复插原样整行）；
  * 顶栏 trailing「清空」（仅历史页且非空）→ `ClearHistoryConfirmDialog`
    （Dialog 窗口壳仿库页 DeleteConfirmDialog：遮罩盖底栏/迷你条、返回只
    关确认框；文案含「不可撤销。媒体文件不受影响。」）→ `clearHistory()`。

2. 测试
----------------------------------------------------------------
- `HistoryRemoveUndoTest` 4 项（core/database，纯 JVM + FakeHistoryDao）：
  remove 摘行 / 行不存在返回 false / undo 原样复插（断点·时间戳逐字段）
  且第二次 undo 返回 false / remove-undo 反复轮转。
  * 测试过程中抓到并修掉一个真缺陷：`undoRemoveHistory` 最初把「没有留底」
    的 `return false` 写进 `storageWrite { … != null }` 块内——块返回布尔
    false 也是非 null，被 `!= null` 判成"写成功"，第二次 undo 恒 true。
    留底查找移到 storageWrite 外（没有留底不是存储故障，是业务语义）。
- 门禁（最终源码全跑）：test **149 套件 / 1038 项 / 0 失败**（基线
  148/1034 + 4 项）、lint 15 份 0 issue、release 29,208,295 B、
  debug 66,222,573 B。
- **附带**：同批修复 scanner bench 批跑偶发挂死（今日两次，详证据 §4）。

3. 真机现象（screenshots/e220-2026-10-25/）
----------------------------------------------------------------
- em-17：播放历史子页（2 项），顶栏「清空 ›」trailing 就位。
- em-18：长按第一张卡 → toast「**已从播放历史移除 撤销**」（撤销 accent
  色），计数 2 → 1，卡片即时消失。

  窗口语义）；对「剧集」卡重做（em-20：0 项 + 空态 + toast 在屏）→

- em-22：顶栏「清空」→ 确认卡（标题/全部 1 条将被移除，此操作不可撤销。
  媒体文件不受影响。/ 取消 · 清空[红]）。
- 确认清空（em-24）：toast「已清空播放历史」，0 项 + 空态「还没有播放记录」。

----------------------------------------------------------------
4. 附带修复：ScanWalkParallelismBenchTest 批跑偶发挂死（根因）
----------------------------------------------------------------
今日门禁两次被同一挂死阻塞（单跑恒过）。jstack 定位：SDK 主线程
`runBlocking` joinBlocking，DefaultDispatcher 全体空转——扫描编排的收尾
续体被排进了**停泊 IO worker 的 ThreadLocalEventLoop**（测试 harness 的
main/default 用 `Dispatchers.Unconfined`，Unconfined 续体链在 IO worker
上二次挂起时，下一跳排进该 worker 的线程本地事件循环；批跑下该 worker
停泊后不再领任务，续体永不执行）。
修复（两处）：
- `ScanHarness` 增加 `dispatchers` 注入口（缺省仍为 TestDispatcherProvider）；
- 基准用例传**全 IO** 的 provider（main/default/io = Dispatchers.IO），
  消除 Unconfined 事件循环陷阱；`runBlocking` 体内再包一层
  `withContext(Dispatchers.IO)`（主线程事件循环保持空闲）。
验证：单跑过 + 全模块强制重跑过 + 全量门禁（含全部 scanner 用例）通过。
任务文档 §7 的 [P3] 观察项就此关闭。

----------------------------------------------------------------
5. 边界
----------------------------------------------------------------
- 长按注入在 API 35 模拟器上的怪癖：零距离 `input swipe 700ms` 与
  `motionevent DOWN/UP` 分进程注入都被判成 tap——可用的是
  `input swipe X Y X+2 Y+2 900`（1px 移动 + ≥900ms）；证据照此采集。
- 撤销窗口 = toast 存续期（约 4s），超时后条目保持已删（em-19 即此状态），
  属既定语义；「撤销后同一媒体再次产生新历史」会覆盖留底快照（窗口极短，
  不做版本对账）。
- 左滑删除未做（设计稿「左滑/长按」二选一的另一路）：网格卡片左滑与横滑
  翻页手势冲突，长按先行；任务条目如要求左滑再开。
- 收藏页长按不注册（无删除语义）；「清空」仅挂播放历史页。
