## 判定

| 观察 | 读数 | 结论 |
|---|---|---|
| `send` 随像素增长 | 1.62 → 3.45 → 5.74 ms | 输入侧（JNI 直传 + native 解码入口）与像素近似线性，1080p 约占 41.7ms 帧预算的 14% |
| `recv` 极小 | 0.13–0.41 ms | 出队本身不是瓶颈（真正的解码耗时被 send 的阻塞语义吸收，见边界） |
| `copy` 极小 | 0.18–0.47 ms | 帧拷贝在 1080p 也只有 0.47ms，**「两趟 YUV 拷贝」不是当前瓶颈**（任务文档 §9.2 的 P2 条目优先级可下调） |
| `rend` 最大头 | 2.97 → 6.43 → 12.81 ms | 与像素近似线性（≈6.2ms/MP），1080p 占帧预算 31%——软解路径上屏是首要优化面 |
| `first` | 20 / 47 / 260 / 322 ms | 首帧延迟随分辨率上升；1080p 的 322ms 与同段 `READY +896ms`（含 extractor/probe/起播准备）分开计，不混为一谈 |
| `qavg/qmax` | 全程 7.1–7.9 / 8 | 队列恒贴 `MAX_READY_OUT=8`，背压持续生效，无输入饥饿 |

## 稳定性

- 三档播放全程 `FATAL EXCEPTION` 计数 **0**；无 native 解码错误（`err=0`）。
- 每 2s 一条限频摘要，起播末强制收尾一条；无逐帧日志（对时序无扰动）。

## 边界（没做什么）

- **只覆盖 LegacyVideoRenderer**（legacy / npff 两后端共用）：平台 `MediaCodecVideoRenderer` 与 `NpFfmpegVideoRenderer` 委托层仍无计数，A/B 只能给软解侧结论。
- **`send` 内含 native 解码推进**：`codec.send` 在解到出队上限时会阻塞，因此 `send` 是「送入 + 被背压卡住」的合成量，不能当作纯 JNI 成本读；真正的 JNI/解码拆分需要一次性拆测量点（E245 后续）。
- 夹具是 testsrc2 合成内容（24fps、无 B 帧、4Mbps WMV2），**不是正片**；60s 长跑、JNI copy 开关对照、功耗与温升、平台 renderer 对照均未做。
- 深链 `content://media/external/video/media/<id>` **不会自动起播**（冷启动也只把 MainActivity 提到前台），本轮播放全部走 UI：库页卡片 → 详情 sheet → 「播放」。
- 单机单 OEM（高通 pipa）；MTK/三星未覆盖。
