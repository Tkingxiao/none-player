## 0. 怎么用这份文档

| 你是谁 | 读哪里 |
| --- | --- |
| 要改一个组件 | §3 令牌 → §4 材质 → §5 配方（按组件查表） |
| 要加一个动画 | §3.9 挑时长令牌 → §6 找场景行 → §7 查参数与触觉 |
| 要做平板/桌面形态 | §8（分档表与形态分派，自足） |
| 要判性能/降级 | §9（含 §9.7 测量纪律、§9.8 渲染热路径纪律），尤其 §9.6 三档表 |
| 要验收 | §14（每条都有可测量阈值）；判定结果见《审查文档.md》§3 |
| 要找下一步改什么 | §15 修改建议（待回写 / 功能级 UI 建议 / 引擎与多设备） |
| 觉得本文和别处冲突 | §2 裁定表 + §13 旧文档引用映射 |

**三条不可违反的纪律**（现有代码已建立，批次 5 只能在其上扩展，不能绕过）：

1. **插件层禁止裸值**：不许出现裸 `tween(ms)`、裸 `CubicBezierEasing(...)`、裸 `dp` 尺寸、裸色值。令牌与配方只在 `:core:ui`，插件只引用。唯一例外是 `:core:ui` 自身与壳层导航（且壳层例外已在 §13 清零）。
2. **动效读值进绘制层**：动画状态只在 `graphicsLayer { }` / `draw*` 的 lambda 里解包，不在组合期 `by` 取值（现状 `npPressScale`/`npHoverLift` 已是正例）。
3. **一色一义 / 一名一值**：一个语义只有一个令牌。禁止"同一个层级两处各写一个 alpha"。

### 3.2 语义色（亮）

`bg` 与 `surface` **同为纯白**，这是刻意设计：亮色下卡片不靠底色差分层，**靠发丝描边与阴影分层**（`npCardSurface` 的 1dp `border` 在亮色下是结构件，不是装饰，删掉卡片会糊成一片）。其余见 `NpInkLight`。关键差异值：`accent #CE5600`（亮色下压暗以保证白底对比度）、`scrim` 为暖灰 @42%、`edge` #fff @55%（白底上的"高光"读作纸边）。

**对比度红线**：`fg/bg ≥ 7:1`，`muted/bg ≥ 4.5:1`，`accent` 作文字色时只允许出现在 `accentSoft` 底上且 ≥ 4.5:1（暗色实测 7.6:1，亮色 5.2:1）。

> **E119 清账（8 根 → 5 根）**：设计稿另有 `Drawer`(.32,.72,0,1)、`Overshoot`(.34,1.3,.6,1)、
> `Tonearm`(.34,1.3,.5,1) 三根，三条自落地起**调用点为 0**——它们的天然消费方在施工期都改成了
> spring：抽屉收尾走 `npMotion(Motion.Drawer)`（时长令牌 + Silk spring）、开关 thumb 走
> `npMotion(Motion.Switch, bouncy = true)`、唱臂落针走 bouncy spring。§14 #2 的"零调用点清零"
> 据此删除（先例：批次 5 删 `Expand`，`Shared` 因 M2 落地才加回）。
> 将来若真出现"这里必须用贝塞尔而不是 spring"的场景，按本表格式**新增**并记出处，不要复活旧名。

**线性例外**（唯一允许 `LinearEasing` 的四处）：主题色插值（§3.9 `Scheme`）、shimmer 位移、波形/进度的**连续推进**、缓冲环旋转。凡"用户能感到的一次性状态变化"都不许线性。

**spring 与曲线并存不矛盾**：曲线用于 `tween/fadeIn/slideIn`，spring 用于 `silkFloat/silkDp/silkOffset/silkSize`。同一处动画只用一种（spring 已含曲线语义，再叠 easing 是重复计算）。

**唯一入口是编译期约束，不只是纪律**（E119）：`npMotion(令牌, bouncy, easing)` 是
"令牌 → 档位倍率 → Reduce Motion"这条管道的**唯一出口**，`silkSpring`/`bouncySpring` 已收为
`:core:ui` 的 `internal`——跨模块直调**编译不过**。此前有 24 处写的是 `silkSpring(Motion.Hover)`
这类"裸令牌进弹簧"，三档倍率与系统「移除动画」对它们完全无效（判定见《审查文档.md》§2 E119）。

### 3.9 时长令牌（`Motion`）与 spring 换算

**换算公式（现状，保留不变）**：

```

silkSpring(ms)    = spring(dampingRatio = NoBouncy, stiffness = silkStiffness(ms))
bouncySpring(ms)  = spring(dampingRatio = MediumBouncy, stiffness = silkStiffness(ms))
```

## 4. 材质系统（五件套，`core/ui/Material.kt`）

**层次模型**（自上而下，z 序与 §4.1 一致）：

| 层 | 成员 | 底 | 分层手段 |
| --- | --- | --- | --- |
| **L0 舞台** | 页面 `bg` | `ink.bg` | — |
| **L1 内容** | 卡片、列表、封面 | `ink.surface` | 1dp 发丝描边（`npCardSurface`）+（仅浮层需要时）阴影 |
| **L2 Chrome** | 顶栏、底栏、迷你条、横条 | `ink.glass` = `bg`（**不透明**） | 1px 顶高光 + 可选底发丝线；**不给阴影**（有阴影会被读成"卡片浮着"，与常驻条冲突） |
| **L3 浮层** | Sheet、模态卡、fs-panel、Toast、菜单 | `ink.surface`（实底） | 阴影 `npShadow` + 顶高光；遮罩用 `ink.scrim` |
| **L4 遮罩/渐隐** | 控制层上下渐变、列表两端 fade、滚出遮罩 | 透明 | `NpMaskFade`（§4.5） |

### 4.1 玻璃（条底）—— R1 的最终形态

- **禁止** `Modifier.blur` / `RenderEffect` 作用于任何**背后有滚动内容或视频帧**的面。这不是"降级"，是定稿。
- 条底 = `ink.glass`（= `bg`），由 `Modifier.npGlassChrome(ink)` 提供纯色底，`Modifier.npGlassSurface(ink, shape, topHighlight, bottomHairline, topHairline)` 提供完整配方。
- 层次靠**光**不靠**透**：顶高光（`edge`）表达"这里有一块实体的边"，发丝线表达"内容到此被干净切断"。

> **施工期澄清（B5-2，2026-10-05）**：横向的条（顶栏 / 底栏 / 迷你条 / Tab 栏）一律走 `npGlassSurface` 完整配方，`npGlassChrome` 只剩**竖条**（`.rail` 导航栏）一个调用点——它需要的就是"一块 `bg` 纯色底"，加形状与高光反而会把 rail 的右边缘画出一道不该有的亮线。原先散在 `NpBottomTabBar` / `MiniPlayerBar` / `NpPageScaffold` 里手画的 `edge` 高光和 `border` 发丝线全部收进配方，两处 `SHELL_EDGE_ALPHA_DARK/LIGHT` 常量删除（其值与 `ink.edge` 的 8%/55% 完全相同，属重复定义）。

### 4.2 顶高光（`npTopHairline` / `npGlassSurface(topHighlight=true)`）

只在**中间段**画并两端淡出：inset 16dp（条）/ 12dp（Sheet），`Brush.horizontalGradient(Transparent → ink.edge → Transparent)`，线宽 1dp，y 偏移 0.6dp。四边等亮就没有玻璃味——光从上方来才有。

### 4.3 发丝线

`ink.border`，1dp。分割线只在**语义边界**出现（列表分组之间、Sheet 头部之下），不做"装饰性横线"；亮色下它是卡片唯一的层次来源，所以卡片描边不算"装饰线"。

### 4.4 阴影（`npShadow`）

设计稿 `0 18px 48px -20px`：大模糊 + 负扩散（Compose 无 spread，用居中高 elevation 近似）。默认 `elevation 18dp`，浮层容器 `NpGlass` 默认 12dp。ambient/spot alpha：暗色 0.40/0.55，亮色 0.14/0.20。**规则**：只有 L3 有阴影；L2 永不；L1 的卡片无阴影（有描边）。 **阴影与底的前后关系（E133）**：`npShadow` 必须写在 `clip/background` **之前**（阴影层在最外、白底画在阴影层之内）——反写会让阴影贴图落进浮层自己的白底，内缘出现灰带、白底看起来像一块错位的白框（用户实报）。参考实现：`NpGlass`、`NpMenuSurface`；六处同族（菜单/Sheet/Toast/长按菜单/信息卡/分段滑块）已统一。

### 4.5 mask 渐隐（R11 新增 `NpMaskFade`）

**签名**：

```kotlin
@Composable
fun NpMaskFade(
    modifier: Modifier = Modifier,
    vertical: Boolean = true,        // true：上下渐隐；false：左右
    fromTop: Boolean = true,         // 渐隐起始边
    size: Dp = 88.dp,                // 渐变长度
    color: Color,                    // **必须与它遮住的那个底同色**
    startAlpha: Float = 0.9f,        // 0.9 而非 1.0：留一点"能看见底下在动"
    stops: Float = 0.55f,            // 中段过渡位
    floorAlpha: Float = 0f,          // 中段 stop 的下限（E118 新增，默认 0 = 不改旧行为）
)
```

**四处必用**：

| 位置 | 参数 |
| --- | --- |
| 播放页控制层顶栏后 | `vertical=true, fromTop=true, size=100dp, color=Color.Black, startAlpha=0.78f` |
| 播放页控制层底栏后 | 全屏 `size=88dp` / 竖屏小窗 `size=56dp`，`vertical=true, fromTop=false, color=Color.Black, startAlpha=0.86f, stops=0.68f, floorAlpha=0.62f`（2026-10-05 两轮用户实报：平板横屏"底栏占比过大"、竖屏"暗带占小窗一半"，160→120→按形态拆分 88/56，控制层内容同步收：进度行上边距 6→2dp、底部收边 8→4dp、`BarCtlButton` 38→32dp；**2026-10-09 E118** 中段由 `startAlpha*0.30`（=0.26）抬到 0.62、过渡位 0.45→0.68，理由见下方澄清 ③） |
| 横向滚动列表两端 | `vertical=false, size=24dp, color=ink.bg`（暗色即黑、亮色即白） |
| Sheet 内容滚出遮罩 | `vertical=true, size=16dp, color=ink.surface`，仅在有滚动条时挂 |

**规则**：亮色主题下不许出现黑渐变（会读成"脏边"）——凡遮在页面底上的渐隐一律取 `ink.bg`/`ink.surface`；只有遮在**视频画面**上的渐隐才允许纯黑（视频不是主题色）。

> **施工期澄清（B5-2，2026-10-05）**：两处与上面签名块的偏差，都是落地时的必要修正，不是改判。
> ① `color` 提到**第一位**、`modifier` 留在原位——`NpMaskFade` 是 Box 里的一个层，调用点总是 `Modifier.align(...)` 传 modifier，让它排在首位会让每一处都写成具名参数。
> ② 第三处（横向列表两端）**不做成组件而做成 modifier**：`Modifier.npMaskFadeEdges(color, fadeSize, startAlpha)`。左右渐隐要在**五个**横向列表上各画两层，用组件就得每个都套一层 `Box` + 两个 `align`；做成 modifier 只多一行。它**常开**不随滚动状态挂卸——列表两端的 `contentPadding` 留白比 24dp 渐隐带宽，最强的一段（`startAlpha`）落在留白里，实际只柔和了卡片边缘，不需要读 `LazyListState`。
> 已验证：暗色与亮色主题下横向列表两端的渐隐取的都是 `ink.bg`（亮色采样到的是卡片白而非黑，无"脏边"）。
>
> **施工期澄清（E118，2026-10-09）：③ 底栏的曲线把控件落在了渐变最弱处**。§14 #9 的"控制层压字处 ≥4.5:1"此前只在**封面取色 scrim** 上验过（整域最差 5.33），视频控制层没做过逐像素采样。补做的方法是把一段**纯白画面**（`b3white.mkv`）播在底栏后面，采局部底色：
>
> | 位置（2560×1600 平板） | 旧曲线底色 | 白图标对比度 | 新曲线底色 | 对比度 |
> | --- | --- | --- | --- | --- |
> | 传输键行 y=1520 | `(189,188,189)` | **1.89:1** ❌ | `(77,77,77)` | **8.45:1** ✅ |
> | 同带下沿 y=1585 | `(64,64,64)` | 10.37:1 | `(46,46,46)` | 13.58:1 |
> | 羽化起点 | y≈1424（alpha 0） | — | y≈1424（alpha 0） | — |
>
> 顶栏同一回合实测 5.10:1（它的行贴着画面上沿，天然落在渐变强段）——**差的是几何不是颜色**：底栏的键在带子中段，那里旧曲线的 alpha 只有 `startAlpha*0.30`。所以修法只动曲线：中段抬到 `floorAlpha=0.62`、过渡位从 0.45 推到 0.68，羽化段仍从 alpha 0 起（约 28dp），带高 88/56dp 不变（"占比过大/占一半"两条实报不回退）。`floorAlpha` 默认 0，其余四处调用点行为逐字节不变。

### 4.6 颗粒（R10：定义、批次 5 不做）

若未来要做：`Modifier.npGrain(ink, alpha)`——用固定种子（`42`）一次性生成 96×96 `CacheImageBitmap` 点阵并平铺，alpha 暗色 0.035 / 亮色 0.018，仅 L0/L1，**播放页与视频 surface 上禁用**，仅 High 档。批次 5 标 P2、不进验收。

### 4.7 封面取色背景（音频模式 / 播放页舞台底）

**算法（照抄，不引 palette 库）**：Coil 请求 `size(128)` 采样 → 缩到 32×32 → 每像素 `score = s * 1.4f + (1f - abs(v - 0.62f))`（饱和度加权 + 亮度向 0.62 靠拢）→ 取最高分像素 → 亮度压到 `[0.28, 0.42]`、饱和度上限 `0.55` 作 scrim 用色。

**用途与数值**：

- 仅听音频模式底：封面 `scale 1.35` + 图像高斯模糊（`RenderEffect`，API 31+，radius 见 §9.6；API 26–30 退化为 8×8 放大马赛克 + 1dp 像素格覆盖）+ 取色主色 @0.30 叠加 + `ink.bg` @0.55 顶部渐隐。
- 控制层 scrim 用主色暗变体（V ×0.35），**对比度 ≥ 4.5:1** 才允许文字压在上面，否则回退纯黑。
- 切集：主色 `tween(AccentShift=400, Silk)` 插值——与主题插值同一实现（单值插值 + 冻结帧），**不许**开 36 个独立颜色动画。

> **施工期澄清（B5-2，2026-10-05）**：手写解码（迷你条缩略图、音频模式底、取色）踩到两条只有真机才暴露的坑，都记在这里，因为它们决定了"什么时候才算有封面"。
> ① `MediaItem.coverUri` 装的是扫描器落盘的**绝对路径**（`…/cache/video_thumbs/<id>.jpg`），不是 uri 串。Coil 会自己把这种串当文件路径，`ContentResolver` 不会——直接 `toUri()` 抛 `No content provider`。统一收进 `NpCoverAccent.coverUriOf()`：含 `://` 才按 uri 解析，否则 `Uri.fromFile`。
> ② `BitmapFactory.decodeStream` 返回的是 **Bitmap 而不是 boolean**，`inJustDecodeBounds=true` 那一段它**恒返回 null**。把它的返回值当解码成败看（`?.use { decodeStream(...) } ?: return null`）会让**每一张**封面都静默解不出来——迷你条封面一直空白就是这个原因。成败只看 `outWidth > 0`。
> 三档已在模拟器逐条对照：轻量 = 8×8 点阵 + 1dp 格线（无 blur）；平衡 = 24dp 模糊 + 主色平涂 @0.30；全效 = 60dp 模糊 + 主色渐变 0.42→0.12。顶部 `ink.bg` @0.55 渐隐在三档下都在（实测顶缘被压到约 0.48 亮度）。

### 5.6 `WaveformSeekBar`（新增，"仅听音频"的主视觉资产）

**目的**：零解码成本把一根进度线换成"有内容的波形"，让音频模式不像播放器空壳。**数据是装饰性的、确定性的**——同一文件任何时候形状完全一致（这点必须写进测试，否则会被实现成每帧随机抖动的"果冻"）。

**签名**：

```kotlin
@Composable
internal fun WaveformSeekBar(
    mediaKey: String,          // 确定性种子源：HistoryEntry.keyOf(item) 同款
    durationMs: Long,
    positionMs: Long,
    bufferedFraction: Float,
    barCount: Int,             // §9.6 分档：Lightweight 28 / Balanced 44 / High 56
    modifier: Modifier = Modifier,
    onSeek: (Long) -> Unit,
)
```

**生成规则（照抄，勿改常数）**：

```
每根 bar i ∈ [0, n)：
  h = hashFnv1a(mediaKey) ^ 上一轮状态，用 xorshift32 推进得到 r ∈ [0,1)
  amp = 0.28 + r*0.52 + sin(i*0.23f)*0.18f + sin(i/n*PI)*0.28f
  amp = amp.coerceIn(0.18f, 1f)
```

- `0.28` 底 + `r*0.52` 随机纹理 + 两个正弦（前者制造细密起伏，后者制造"整段有起有落"的乐句感）。
- 种子必须含 `mediaKey`，**不许**用 `Random()` / 时间戳 / 帧号。
- 缓存：`remember(mediaKey, barCount)` 算一次 `FloatArray`，滚动与重组成因都不重算。

**绘制**：bar 宽 3dp、间隙 2dp、圆头；已播 `accent`，未播 `fgSoft`（音频模式底在封面上，取 `Color.White@0.18`），已缓冲段 `Color.White@0.10` 覆盖。播放中位置**连续推进**用 `LinearEasing`（§3.8 线性例外）；点击/拖动行为与 `NpSeekBar` 同（26dp 触控带、thumb 无、以"当前 bar 高亮"替代）。

**接法**：仅"音频模式 + 详情大封面"两处；**视频播放页仍用 §5.4**（波形会误导"这是音频文件"）。

## 7. 组件级动效参数

### 7.1 反馈类（即时性优先）

| 场景 | 值 |
| --- | --- |

| hover 上浮 | 2dp；`Panel 180`；仅 `LocalNpHoverEnabled` |

| 输入/聚焦 | `Field 150` |
| 反馈上限 | 任何"点了要有反应"的路径 ≤150ms（红线 1） |

### 7.2 页面转场与共享元素

```
路由（KernelNavHost，收编现有裸 tween）：
  push: fadeIn(NavFade 240) + slideInHorizontally(NavEnter 280){ it/4 }   Silk
  pop : fadeOut(NavExit 180) + slideOutHorizontally(NavEnter 280){ -it/4 } SilkExit
  —— 方向感保持现状，只把三个毫秒数换成令牌（Q20 收敛，例外清零）

卡片 → 播放页（sharedTransitionLayout）：
  封面: sharedBounds(A→B) Shared=300，Emphasized
  其余卡片元素: fadeOut 150
  播放页控制层: fadeIn Overlay=280，延迟 150ms（等视频就位）
  返回: B→A 逆向；播放页内容先 fadeOut 120
```

**可中断（硬要求）**：转场中返回手势立即反向，从当前 presentation 值开始；**禁止**用 `isTransitionRunning` 之类的锁阻塞输入。

**Tab 内容转场（2026-10-11 E128 定稿；取代 E127 的"8dp 淡移"）**——用户实报"要的是界面的切换动画，不是底部标签栏的"，且旧实现**从未真正播放**过（见下），本轮连根一起重做：

```
标签内容转场（KernelTabScaffold，四标签切换）：
  进场: fadeIn(NavEnter 280, Silk) + scaleIn(0.98→1, NavEnter, Silk) + 方向视差位移（NavEnter, Silk）
  退场: fadeOut(NavExit 180, SilkExit) + scaleOut(1→0.98, NavExit, SilkExit) + 同向视差（NavExit, SilkExit）
  位移轴跟随导航轴：紧凑档底栏横向 → 水平 20dp；Rail 纵向 → 垂直 14dp（轻量档 / Reduce Motion 全程并掉）
  方向: selectTab 里算 from/to 符号（0 = 未知 → 只淡不挪），不去问转场作用域
  条上三件（胶囊滑动 / 图标 0.9→1 / 色变）仍走 Tab=220，不受本节改动
```

- **四件套的分工**：`NavEnter/NavExit` 是"路由转场"三兄弟的语义复用——Tab 是内层 NavHost 的**平级目的地**，内容转场本来就是一次路由转场；`Tab(220)` 只留给标签栏自己的三件。280 的 Silk 前段极快（约 40% 时间走完约 90% 进度，读起来接近 200ms 响应），退场 180 加速离开（进慢出快，§3.9）。
- **不做整页滑**：2026-10-12将原36/28dp缩为20/14dp、缩放回0.98，减少重复进列表的归位幅度；保持同向视差与状态恢复。
- **E128 修掉的真实缺陷（内容过渡从未播放的根因）**：`popUpTo(选中页, inclusive=true)` 与 `navigate` 在同一导航事务里执行时，navigation-compose 2.8.5 的 `popEntryFromBackStack` 会把被弹出的条目标记为 **DESTROYED**（`transitioning=false` 分支），它随即从 `visibleEntries` 消失；而 NavHost 的 `transitionSpec` 有一条硬规则——**初态不在 visibleEntries 就整个跳过动画**（走 `EnterTransition.None togetherWith ExitTransition.None`）。表现就是：胶囊在飞、内容硬切。修法是切页前先调 **`ComposeNavigator.prepareForTransition(离场条目)`**（公开 API，原为预测性返回而设）把它标成"过渡中"，弹出分支改走"保留 CREATED 等过渡收尾"，条目留在 `visibleEntries` 里——动画才真正播放；收尾由 NavHost 自己调 `onTransitionComplete` 销毁，`saveState/restoreState` 的存档语义不变（E53"栈内永远只一个 Tab / 返回=退出"不破）。
- **形态自适应**：紧凑底栏水平20dp，Rail垂直14dp，方向轴与导航轴一致。

**共享元素实际落地（2026-10-08）**：官方 `SharedTransitionLayout` 的导航集成在本工程 `navigation-compose:2.8.5` 上不存在（AAR 符号扫描为 0），按约定走**手绘轻量版**：一次性交接件 `NpCoverFlight`（卡片起飞记 `(mediaId, 窗口机位)`、目标页取走、1.5s TTL）+ 播放页从机位补间到舞台矩形（`Shared=300` + `Emphasized`，末段 15% 淡出交给视频）；动画值只读在 `layout/graphicsLayer`。判定见《审查文档.md》§2（双机实测：手机抓到飞行中帧、平板无残影）。

### 7.3 手势物理：速度接棒与动量投影

```kotlin
// 拖动中：1:1 赋值，无动画（禁止任何 tween）
// 释放：把 tracker 速度交给动画
val v = tracker.calculateVelocity().x
val projected = target + (v / 1000f * damping / stiffnessFactor)   // Apple project() 简化式
animatable.animateTo(projected.coerceIn(0f, max),
                     silkSpring(Expand), initialVelocity = v)
```

**三处必须实现速度接棒**：进度条 seek 释放、Sheet 下滑关闭、控制层显隐打断。其余动画不许自写 `Animatable`。

### 7.4 越界橡皮筋

`rubberband` **已于 E134 删除**（零调用清零）：亮度/音量与下拉刷新从未接上，底部 Sheet 的上拉过头在真机实报里被读成缺陷——没有"更高一档"可去时上拉一律钳制为 0。将来真出现"拖出界要阻尼跟随"的场景按本节格式新增再记出处。

### 7.5 Haptics 映射（新建 `core/ui/Haptics.kt`）

```kotlin
enum class NpHaptic { Tap, LightTap, Tick, Segment, Long, Reject, Warning }
@Composable fun rememberNpHaptics(): NpHaptics   // performHaptic / performHardwareTick
```

| 语义 | 类型 | API<31 回退 | 场景 |
| --- | --- | --- | --- |
| `Tap` | `KEYBOARD_TAP` | `VIRTUAL_KEY` | M1 卡片、M6 播放暂停 |
| `LightTap` | `CONTEXT_CLICK` | `VIRTUAL_KEY` | M3 迷你条出现 |
| `Tick` | `CLOCK_TICK` | `VIRTUAL_KEY` | M4 Tab、M7 松手、M8 双击、M14 刷新触发 |
| `Segment` | `SEGMENT_TICK` | 无（**跳过**） | M11 Sheet detent |
| `Long` | `LONG_PRESS` | `LONG_PRESS`（API 26 有） | M9 长按、M7 拖动开始 |
| `Reject` | `VIBRATE_HEAVY`/`REJECT` | `VIRTUAL_KEY` | M10 边界、M18 错误 |
| `Warning` | `VIBRATE_LONG` | `VIRTUAL_KEY` | §5.5 确认卡（危险操作） |

**规则**：与动效**同帧**触发；一屏一次以上即算滥用（不给滚动、不给 hover、不给文字输入逐字）；`isHapticFeedbackEnabled=false` 时全静默。

### 7.6 可中断与并发

同一目标只允许一个动画持有者：状态转换用 `Animatable` 而**不是**多个 `AnimatedVisibility` 叠加；打开弹层时控制层自动隐藏计时**暂停**（§5.5 层级规则 2）。

## 9. 性能与降级

### 9.1 预算（可测量，§14 验收依据）

| 指标 | 阈值 |
| --- | --- |
| 列表滚动 jank（`adb shell dumpsys gfxinfo` `Janky frames`） | ≤ 5%，且 ≥ 60fps 的 P95 帧时 ≤ 20ms |
| 反馈到画面变化 | ≤ 150ms |
| 动效期间重组范围 | 单卡/单条，**不允许**整页重组成交代价 |
| 动画对每帧组合开销的贡献 | 0（所有动画值读在绘制层） |
| Release APK 体积增量 | ≤ 0.5MB（R9 自绘图标因此可满足；若引 extended 会 +5MB，视为不合格） |

### 9.2 绘制层纪律（现状正例的推广）

`graphicsLayer { }` / `drawWithCache` 里读 `State.value`；禁止 `val x by animateFloatAsState(...)` 后在组合期用。已落地的两处正例（旧档 §11 曾记为反例）：**位置读进 seek 轨所在组件**（`PlayerScreen` 只传 `State<Long>` 下传、显示位置走 `derivedStateOf`）、**手势 HUD 值读进 HUD 自身**。同族纪律：`LaunchedEffect(位置状态)` 把位置读进组合 = 每次上报（引擎 250ms 一跳）重组整页——要用 Flow collect（弹幕覆盖层同款，`2fa81b0`）。

**E120 补两条只有实测才能立起来的细则**：

1. **"订阅点在哪，失效就打到哪"包括局部函数**。把 `val positionMs by player.positionMs.collectAsStateWithLifecycle()` 从页面顶挪进页面里的**局部** `@Composable fun ProgressBlock()`，实测**没有**收窄重组域——仅听音频页仍按 4/s 整页重组（41 次/12s）；把这两个订阅拔掉，同一窗口整页重组 **0 次**。改成**文件级** `private fun AudioProgressRow(...)`（独立签名 = 独立重组域）后整页归 0、进度行照常走字。结论：**进度类订阅必须落在文件级 composables 里**，局部 composable 函数不算独立重组域。
2. **缓冲进度与播放进度同节奏**。`player.bufferedPositionMs` 也是 250ms 一跳，第一次只搬 `positionMs` 时整页仍是 37 次/12s——**两条都得进叶子**。同理 `session.nowPlaying` 含 `positionMs`，只要 `by` 解包它整页就跟着走；为此会话层加了 `nowPlayingSummary`（位置无关投影，`distinctUntilChanged` 实测 4/s 上游 → 0 次下游发射），只问"在播什么"的地方（仅听页、类 PC 右栏的 `isOccupied`）一律改订它。

修后实测：仅听音频页整页重组 **41 → 0 次/12s**；类 PC 内嵌右栏 `InlinePlayerView` **43 → 2 次/12s**。**顺带证伪一条推论**：内嵌栏的 `AndroidView` 一直被 Compose 正确跳过，同窗口 `attachSurfaceTo`（跨进程重挂视频表面）计 **0 次**——"4/s 重组会重挂表面"不成立，重组的代价只在父作用域自身白跑与 `Brush`/spec 的重复分配上。

### 9.3 Reduce Motion（系统"移除动画"）

`LocalNpReduceMotion` 已全局单点下发。统一入口（**本批新增，取代各组件手工判断**）：

```kotlin
fun <T> npMotion(durationMs: Int, reduceMotion: Boolean): FiniteAnimationSpec<T> =
    if (reduceMotion) tweenOrFade(120) else silkSpring(durationMs)
```

约定：所有 slide/expand/scale → **≤120ms 纯 fade**；spring → `tween(120)`；stagger 取消（整组一次淡出）；主题冻结帧**保留**（本身是非位移淡出）；共享元素退化为 `Crossfade`。减弱动态 = 更少更柔，不是零反馈——触觉与颜色变化不关。

### 9.4 播放中自动降一档

`PlaybackSession.isActive && 视频正在解码` 时（不区分用户档位）临时：关 stagger、关 shimmer、关水波/冒泡、波形 bar 数取 Lightweight 值、封面取色只在切集时算一次。**反馈类动效（M1/M3/M5/M7）不降**——降了会被感知为"卡"而不是"省电"。

### 9.5 图像模糊成本（R1 唯一的 blur 允许点）

`Modifier.blur` 在 API < 31 是 no-op。因此：音频模式背景在 API 31+ 走 `RenderEffect`（radius §9.6），26–30 走"8×8 降采样放大 + 取色叠加"近似（视觉等效、成本恒定）。**永远只模糊一张静态图**，不模糊视频 surface。

### 9.6 三档性能模式（`NpMotionQuality`）

**判据**：设置覆盖（设置 → 外观与关于 → **性能模式**，三档「轻量 / 平衡 / 全效」，默认"平衡"）> 自动判定。自动：`ActivityManager.isLowRamDevice` 或 `SDK_INT < 29` → **Lightweight**；`SDK_INT >= 31` 且非低内存且（当前无视频解码 或 `isDesktopLike`）→ **High**；其余 → **Balanced**。运行时随 §9.4 临时降档（不改用户设置）。

> **施工期澄清（B5-1，2026-10-05）**：上面两句按字面同时成立会打架——"默认平衡"意味着**没碰过设置的用户永远拿到 Balanced**，自动判定那一支就成了死代码；而"设置覆盖 > 自动判定"若理解为用户档可以**抬高**设备实况，低内存机上选"全效"就会把 60dp 图像模糊和 56 根波形压进解码期。落地的规则取两者的工程解：**用户档是上限，自动判定与 §9.4 播放降档只能往下压**——`生效 = lowerOf(用户档 ?: 自动档, 自动档)`，再 `forPlayback()`。于是：默认用户 = Balanced；弱机用户 = Lightweight（他选全效也上不去）；大屏 / 无解码且用户显式选全效 = High。若判定这条读错了（例如希望"用户选了就必须照做，弱机也认"），改 `Theme.kt` 里 `lowerOf` 那一行即可，其余管道不受影响。

### 9.7 测量纪律（2026-10-08 两个对照实验的教训，不可违反）

- **绝对 jank% / 帧时长在本环境没有判定力**：模拟器每帧基线 ~80ms（144Hz 面板预算仅 6.9ms），跨会话对比"0.42% → 60–77%"是**模拟器配置差异**不是应用回归——曾有存量"回归"结论据此立账后又被实验更正。**只有同条件内容变体 A/B**（同一会话内只翻一个变量）才作判据。
- 怀疑谁就**先把谁关掉再量**（一次构建、5 分钟）：禁用封面位图 → jank 同值；纯文字页 → 同基线。两步即把"滚动卡在封面解码"的前提证伪。
- 同一实验结论必须能复述成数字（对照前后各量一次）；量不出收益的改动要如实标注"确定的减法、本机测不出差"（如四处绘制层 `clip` 卫生，`28bc433`）。
- **A/B 必须来回装包**（base → new → base，2026-10-10 E123 补）：长时间测试会让设备**单向漂移**——实测同一条 1GB 文件的新鲜探测在一小时里从 1.1s 漂到 2.5–4.3s，不来回跑就会把漂移读成回归、或把回归读成收益。拿不到双份数字时，只报**机制可判**的那一段（如"缓存命中"有专行日志可查）。
- **帧类指标只报绝对计数**（E125 补）：`frames / janky / slowUI / slowDraw` 可比，`janky%` 与 `p50` 在**帧群体变了**时不可比——去掉一批逐帧廉价帧之后，剩下的都是真活，百分比与中位数会**变差而实际变好**（实测：帧数 238→119 的同时 p50 从 48ms 涨到 105ms）。

### 9.8 渲染热路径纪律（弹幕覆盖层沉淀的两条推广，2026-10-08）

- **逐帧热路径禁 O(N) 全表扫描**：`DanmakuPlanner.plan` 的窗口截取改二分（列表升序契约），10 万条 **382.6µs → 16.1µs**；任何"每帧过滤全集 / 每帧重测文本"的写法都要换成二分、索引或缓存（提交 `2fa81b0`）。
- **暂停停帧**：非 Playing 态画布不逐帧重绘（冻结画面自然保留），但**锚点壁钟要逐帧保持当下**——否则恢复播放的瞬间会把整段暂停时长外推进显示位置（弹幕窗口闪跳）；暂停态 seek 补一次重绘。排版结果（`measureText` 等）按 (文字, 字号) 分代缓存，字号变化整体失效。

### 9.9 切换链路与逐帧调用纪律（E123–E125 沉淀，2026-10-10）

- **E80 的探测闸一条都不许松，但探测结论可以按指纹缓存**：`FormatProbe` 的缓存以 uri 为键、以 `sizeBytes + lastModifiedSec` 为失效判据（与 E111 断点校验**同一条约定**），`Unknown` 不入库——"放行"不等于"验证过"。新增装载路径仍然必须过 `probeThenLoad`，快慢的差别只在命中与否。
- **投机活必须让位于真实活**：邻域预探测（L2 的探测侧一半）要同时满足三条才允许跑——① 当前集缓冲领先在播位置 ≥30s；② 真实装载一开始就取消它；③ 探测循环内部可取消（`ensureActive()`）。缺第③条时实测一次真探测被还在跑的预热挤到 **589ms → 1799ms**：**不可取消的投机 IO 会比不做投机更慢**。
- **无限动画的取值只许出现在绘制相位**（§9.2 的推广）：`Animatable/Transition.value` 解在组合期 = 每帧重组自己 + 每帧造对象；骨架屏（`NpSkeleton`）此前正是这种写法，在"和真正内容抢帧的那一方"身上。规矩：取值进 `drawBehind`/`graphicsLayer`/`drawWithCache`，刷子·几何·`Stroke` 一律 `drawWithCache`（E121 立的规矩，本轮补上漏网的 `npTopHairline`）。
- **逐帧下发的平台调用先比现值**：窗口属性（亮度）、`setStreamVolume`（音量）这类每指针事件一次的 relayout/binder，必须"实际值真变才发"；而且比的是**平台上的现值**，不是自己记住的那个整数——用整数比会让"进页第一次真正下发"被自己的守卫吞掉。同理，**停留计时不要每次事件 `cancel + launch` 一个协程**，写一个时间戳 + 一条自延后的循环即可。
- **主题层的输入只能是布尔快照**（§9.4 落地教训）：播放中降档需要"在不在解码"这一个比特；若改订 `nowPlaying`/进度流，主题层就随进度每秒 4 跳，**一次降档变成一次全应用重组**——那比它想省的帧贵得多。跨模块共享用 `:core:media` 的进程级对象（`NpDecoding`，与 `ProbeMemo` 同一姿势），不给 `plugin-*` 之间开新依赖。

### 9.10 构建类型与采集口径（E129 沉淀，2026-10-11，真机 23043RP34C）

- **调试包与 release 包的数字不可混用，且必须在同一段脚本下对照**。同一台设备、同一段自动滑动（`tools/jank.ps1`）：
  **debug 826 帧 / 244 janky（29.54%）/ slowUI 205 / p90 20ms** → **release 1019 帧 / 9 janky（0.88%）/ slowUI 5 / p90 8ms**。
  同一份 atrace 的帧间隔直方图更直白：**debug 27.6% 的帧跨 2 个 vsync，release 只有 0.4%**（144Hz 面板）。
  差的是**代码执行形态**不是应用逻辑：`Jit code cache` 锁竞争切片 debug **6257** 条 / release **0** 条，`Compiling baseline` 236 / 88，主线程 sched 运行时间 **646 → 364 ms/s**。
  推论：**拿调试包判"应用滚动掉帧"必然误判**——先问包型，再谈优化（本仓装机默认是 `app-debug.apk`，这正是 E128/E129 两次实报的共同前提）。
- **`atrace` 必须带 `-a <包名>`**：Compose 自己发的切片（`checkForSemanticsChanges`、`sendAccessibilitySemanticsStructureChangeEvents`、`Recomposer:*`）走 `TRACE_TAG_APP`，**不带 `-a` 一条都采不到**；而框架切片（`Choreographer#doFrame`、`traversal`、`postAndWait`，`TRACE_TAG_VIEW`）照常出现。E129 第一版 release 轨迹因此显示"语义链 0 条"，差点记成"release 下语义链消失"的假结论。
- **主线程占用要用 `sched_switch` 算，不要用切片 inclusive 相加**：切片 inclusive 会重复计数嵌套；而 B/E 栈若按 `B|pid|` 的**进程 pid** 分桶，会把主线程与 RenderThread 混进同一个栈，实测把 `Choreographer#doFrame` 的 p50 从 **1.91ms 抬成 5.46ms**（2.9 倍假象）。按 trace 行首的 `comm-tid` 分桶才对。
- **无障碍语义链是主线程最大单项，但它不是"应用写错了"**：两包都跑，debug **7.18ms/次**、release **2.62ms/次**（R8 优化后便宜 2.7 倍），量级 **177–204 ms/s**。它的触发源是懒列表滚动期子节点增删（结构性变更事件），派发次数与"重要节点数"成正比；`enabled_accessibility_services` 在 MIUI 上**写不进去**（`settings put` 回 `Bad arguments`，总开关置 0 后 `dumpsys accessibility` 仍报服务 Bound），所以"关服务再量"在本机**拿不到有效 A/B**——与用户实报一致，不要把它记成"关闭成功"。
- **`mergeDescendants` 必须挂在 clickable 之外，`role` 交给 clickable 自己**：`Modifier.semantics { role = Role.Button }` 另挂一处 = 同一个布局节点**多出一个语义节点**（uiautomator 实测每张卡多一个 `class="android.widget.Button"`、`clickable="false"` 的子节点）；而 `.semantics(mergeDescendants = true)` 写在 `clickable` 内侧时，合并的是它**内侧**的后代，卡片在无障碍树里依旧是"1 个可点 View + 4 个 TextView"。两处改对后 debug 侧每帧语义链成本 **2.12 → 1.75 ms/帧（−17%）**。

### 15.4 仅听音频的两块能力（均需引擎扩展点前置）

- **EQ**（**E114 已落地**）：仅听页「均衡器」chip → 面板（总开关 + 段滑杆 + 平坦/低音/人声/明亮四预设）。**段数与量程不写死**——由引擎侧实测 `Equalizer` 后经 `SessionExtras` 回传，UI 只画归一 -1..1、映射与钳位在服务侧做（客户端猜量程必然越界）；预设是**形状函数**（段序 → 增益），3/5/8 段保持同一味道。`audioSessionId` 始终不外露：效果实例建在会话侧，跨进程只传意图。
- **音频偏移**（**E114 判为技术边界，不做**）：media3 无音频延迟通道（`DefaultAudioSink`/`MediaCodecAudioRenderer` 无 offset，`PlaybackParams` 只管速率）。真做需自建带延迟线的 `AudioSink`——音频管线级改造，回归面覆盖全部播放路径；**不用字幕偏移反向冒充**。候选路径与判定见《审查文档.md》§2 E114、《任务文档.md》A2-10。

## 附录：第二播放引擎（KitePlayer）评估与建议（2026-10-05 评估，结论仍有效）

> **可行性：高。必要性：当前低。建议"共存试点"而非"接管"。** KitePlayer = yuroyami 的 KMP 纯 Kotlin 播放器（KiteFFmpeg 内嵌 + MediaCodec 硬解，Apache-2.0，0.2.0 pre-1.0，单一维护者）。

- **可行性**：本项目 `VideoPlayer` 契约天然多引擎（`PlayerEngineProvider` 按 `engineId/priority/supports(mimeType)` 分发）；`state/positionMs/durationMs/cues/queue` 等成员均可低/中成本映射。新插件 `plugin-player-kite`（Provider + 适配器 ≈ 400–600 行）一个迭代内可试点。
- **能力增量（共存的理由）**：① libass 全特效 ASS 字幕（卡拉OK/动画/内嵌字体）——本项目纯文本 + PGS 位图之外最实在的能力差；② 10 段 EQ / 响度 / 平衡 / 音频延迟 / ReplayGain；③ 字幕延迟/样式/双轨开箱；④ 把「硬件解码优先」升级为真三态（自动 / 强制软解 / Kite）。
- **风险**：0.x API 不稳定（锁版本 + 适配层隔离）、单维护者长期不确定、二次内嵌 FFmpeg 的体积增量（+10–20MB 待实测）、LGPL 证明义务翻倍。
- **路线**：① 现在不动（引擎层冻结，资源全投任务文档 A 组）；② P1 后期试点（`supports()` 限定 ASS 特效 / 音频增强场景，复用 4x3/16x9/21x9/9x16 测试矩阵 + 补样本）；③ 决策点（试点验收后）：升级默认（格式矩阵全绿 + 0.3+ API 趋稳 + 体积 <15MB）／维持共存／放弃（音质与字幕延迟改在 Exo 侧 `trackSelectionParameters` 实现）。
- **不采纳**：全量接管——media3 MediaSession 通知集成、`PlaybackService` 修复史、探测闸 + 失败闩锁、Media3Avi 等已真机验证的引擎层资产要在 0.x 库上重做，风险收益比不成立。
