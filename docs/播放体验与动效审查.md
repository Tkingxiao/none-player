## 判定与边界

- 已实现：当前源码能确认路径，不等于所有设备通过。
- 已验证：必须附本轮测试或设备证据。
- 待修：源码存在确定错误。
- 待测：需要素材、硬件或测量，不假称已复现。
- 规划：新增能力或结构调整，不冒充 bug。

首批仅使用 `emulator-5554`（手机）和 `emulator-5556`（Pixel Tablet）。用户随后授权真机测试，B3菜单批次增加 `已授权平板`（Android 14），仅播放专用合成素材，不清除应用数据。设备脚本默认模拟器，真机必须显式启用。尺寸模拟不等于真实铰链、多窗口、HDR、直通或温控验证。

## E135 平板横竖屏交接、「我的」落点与触觉批次

2026-10-14 真机实报，两轮。第一轮四条，第二轮三条（其中两条是第一轮的落点修正）。一台已授权平板（1800x2880 / 400dpi，sw720dp，横屏判为类 PC）逐条复现、逐条复验。

### 根因与实施

- **详情页跨形态残留（"视频详情外显"）**：`detailItem` 只在 `isDesktopLike` 下有入口（`LibraryScreen` 的 `openDetailOrPlayer` 与长按菜单 `onDetail` 两处都拿它把关），却是 `rememberSaveable` 的页内态——转竖屏后照样活着，而竖屏点卡片是直接进播放页，这一页在竖屏根本没有入口。**第一轮按"转出该档就清空"做，被用户驳回**：转回横屏时左栏只剩列表（"应该是横屏的剧集页"）。现行做法是把约束落在**渲染分支**而不是状态上：`val detailOpen = windowInfo.isDesktopLike && detailItem != null`，顶栏标题/返回键/`BackHandler`/`LibraryStage` 四处一律认 `detailOpen`。竖屏不画它（不再外显），转回横屏它自己回来。
- **竖屏点卡片→转横屏，左栏没有剧集页可落**：竖屏那次点击压根没经过详情页，`detailItem` 是空的。新增内核值通道 `NpDetailRequest`（与 `NpInlinePlayRequest` 反向、同一姿势：`plugin-player-ui` 发、`plugin-library` 消费），播放页在交还右栏前把会话当前项递过去，媒体库据此落位。**带 1.5s 时限**：媒体库可能不在当前 Tab（用户在「我的」里看的视频），没人消费的迟到值不能在某次无关的切回时凭空跳详情页。
- **竖屏播放页转横屏"直接全屏视频"**：本页版式恒等于"窗口横向即沉浸全屏"。类 PC 档的画面归属是右栏，竖屏期间进的播放页在窗口转横后仍占整屏就成了错位。修法：`PlayerScreen` 记 `isDesktopLike` **边沿**，只在"竖 → 类 PC"那一次把画面交还右栏并退页（复用返回键那条 `returnToBrowsePane`：快照 + `popBackStack`）；从右栏「⛶」进本页时窗口本就是类 PC，那次不动。
- **交还后落回列表（会话无当前项）**：装载失败或队列已空时右栏根本不会出现（`isOccupied()` 为假），那时退页等于把人丢回列表。真机拿一条本机解不了的 xvid 样本复现过。修法：交还条件加一条 `currentItem != null`，与右栏 `isOccupied()` 同一判据。
- **右栏播放转竖屏掉成迷你条**：右栏由 `isDesktopLike` 把关，转竖屏外壳收回该栏、Surface 随之释放，会话还在跑却没有承载者，读起来就是"没继续播、进了后台播放"。修法：`PlaybackPaneChrome.Render` 在收回之前把播放交给播放页（**不带** `fs=1`——那会反向请求横向，跟刚发生的转屏对着干）。
- **播放页弹层跨形态残留**：Activity 声明 `configChanges`，转屏不重建，`fsMenuPage` / `fileInfoVisible` / 选集 / 章节 / 字幕 / 音轨 / 画面 / 更多全是页内 `remember`，横屏打开的东西原样盖在竖屏新版式上。修法：以 `windowIsPortrait` 边沿调 `dismissAllOverlays()`——与锁定、进 PiP 同一收口，不另立清单。
- **「我的」播放历史 / 收藏跳首页**：原走 `NpTabChannel.request("home", …)` + `switchTab("home")`，Rail/底栏选中态跑到首页、返回也落首页。修法：改成本 Tab 内的**准二级页**（`ProfileSubPage` 页内态 + `NpAppTopBar` 返回 + `BackHandler`），卡片复用首页同一份 `RecentCard`。跨 Tab 通道就此没有生产方，`NpTabChannel` 删除（同文件的 `NpThemeToggle` 迁到 `NpThemeToggle.kt`）。
- **手机版"切界面一路震"**：三处导航族触觉。`core:ui` 的 `npPressScale` 在**每一次抬起**下发 `Tap`，而它铺满卡片/图标钮/底栏钮，等于每次导航都响；`KernelTabScaffold.selectTab` 每次切 Tab 一发 `Tick`；迷你条出现/收起各一发 `LightTap`（用户没碰任何东西）。三处全部撤除。**保留**：长按（`Long`，删除等破坏性菜单的入口）、破坏性确认（`Warning`）、进度条擦洗与舞台手势这类直接操纵反馈、边界与失败的 `Reject`。

- **转屏动画闪屏（用户录屏逐帧取证）**：`Screenrecorder-2026-10-14-17-51-21-714.mp4` 拆到 207 帧，第 79 帧与第 83 帧是**两层页面同时半透明叠在一起**——播放页与详情页、首页与剧集页各自交叉淡入，撞上系统转屏动画。根因是转屏触发的自动导航复用了"用户翻页"的转场：`KernelNavHost` 的 enter/exit/popEnter/popExit 一律 fadeIn + 整页横向位移，`LibraryScreen` 的 stage `AnimatedContent` 又叠一层 8dp 方向位移。修法：新增 `NpFormHandoff`（600ms 时限的一次性标记，转屏交接在发起导航前打点），上述两处转场读到它就走 `EnterTransition.None / ExitTransition.None`。用时限而不是"消费即清"，因为一次交接会被 enter + exit 两个 lambda 读到，先读的清掉会让后半截照旧动画。
- **"进播放页返回后首页像被下滑、继续观看被挡住"（不是滚动）**：实测冷启动首页 `最近添加` 在 y=914，一次"点卡片 → 播放页 → 返回"后落到 y=325，位移正好等于「继续观看」整节高度、且边界干净无裁切。根因是 `history.recent` 被声明成 `Flow`，调用方只能写 `collectAsStateWithLifecycle(initialValue = emptyList())`——**那一帧的空列表不是"确实没有记录"而是"还没读到"**，于是「继续观看」整节在那一帧消失，而 `LazyListState` 按**下标**（不是 key）恢复滚动位置，正好恢复到下一节的头上。这与 E126（`scanFolderUris` 初值给 emptyList）、E105（媒体列表首帧）是同一条坑的第三次出现。修法：`HistoryRepository.recent` / `favorites` 按 `stateIn` 的真实产物声明成 `StateFlow`，四处收集点一律去掉 `initialValue`，首帧直接取现值。

1. **右栏比配置慢一帧**：`20:42:50.893 pane progress=1.0 desktop=false`。`animateFloatAsState` 即使给 `snap()` 也要下一帧才落值，所以转屏第一帧右栏的 TextureView 还挂在树上、列表还被挤成 320dp——播放页的 Surface 同时挂上，屏幕上就是**两个视频实例**。这就是"一大一小两层"。
2. **导航到落页之间隔着几百毫秒**：`mark()` 在 `50.783`，NavHost 的 enter/exit 却在 `51.352` 才被求值——**569ms**。这段里屏幕上躺着的是首页。原因不是转场没免掉（`silent=true` 全都读到了），是主线程被转屏那一帧整棵媒体库树的 measure/layout 占满，`navigate()` 写进 StateFlow 后要等这段时间才轮到 NavHost 重组。
3. **没在播时压根没有路线**：`handoffLeavingDesktop now=false was=true paneRoute=false` + `libraryStage silent=false`。`panePlayerRoute` 只有右栏在组合时才登记，而右栏由 `isOccupied()`（会话有没有当前项）把关。没在播 → 没路线 → 不导航 → 也不 `mark()` → 详情页在竖屏收成首页那一下**照旧交叉淡入**，撞上系统转屏动画。用户看到的"闪屏 + 露出剧集封面"就是这一条。

另外确认：`window.attributes.rotationAnimation = ROTATION_ANIMATION_JUMPCUT` 在这台 HyperOS 平板上**不生效**，录屏里 116-176 帧是完整的 3D 透视旋转过渡。系统动画不可依赖，只能保证"被旋进去的那张图本身是对的"。

### 实施

- **右栏随档位当场拆**（`KernelTabScaffold`）：新增 `paneShown = if (isDesktopLike) paneProgress else 0f`，列表宽度、右栏渲染、`detailPaneOccupied` 三处一律读它。离开类 PC 那一档右栏是"没了"不是"在收"，不该等动画。
- **档位一变就 `mark()`**（`NpFormHandoff.noteForm`）：原来只在真要导航时打点，第 3 条证据说明"没有导航的形态变化"同样有整页重排要按住。`noteDesktop` / `handoffLeavingDesktop` 合成一个 `noteForm`。
- **交接覆盖层**（`NpHandoffCover` + `NpFormHandoffCoverOverlay`，挂在 `KernelNavHost` 的整壳之上）：盖住第 2 条那几百毫秒。右栏在播就盖抓到的那一帧（`ContentScale.Fit` + **顶对齐**，竖屏播放页的舞台贴着顶栏，居中会让画面在接手时往下跳半屏），没在播就盖纯黑（落点那页出画前本来就是黑的）。播放页 `stageRectInWindow` 量到尺寸即 `requestCoverEnd()`，120ms 淡出；另带 1200ms 兜底时限，导航被吞也不会一直压着。
- **详情页在竖屏的落点**（`offerDetailRoute`）：媒体库在类 PC 档把 `detailItem` 登记为第二条路线，优先级低于右栏。竖屏没有详情页这一档（竖屏点卡片是直接进播放页），所以详情页在竖屏的对应物就是播放页。
- **`play=0` = 只装载不起播**：新路由参数 → `PlayerScreen(startPlaying=false)` → `ensureSessionPlaying(prepareOnly=true)`。与既有的 `autoPlay` 不是一回事——`autoPlay` 只在"会话里已经是同一个媒体"那半边说话（E104），新装载那半边照旧起播，媒体库点卡片要的就是它。**A08 在这里一并收掉**：引擎的 `setQueue` 末尾恒有 `c.play()`，所以 `prepareOnly` 必须显式 `player.pause()`，不然是先播一瞬再停、位置还会往前走。播放页的中央播放钮同时认 `Ready`，否则未播放态只剩底部一条播放键。
- **`playerPageAlive`**：播放页在栈上时形态变化由它自己适配，交接不许再推第二个播放页（否则横屏里从详情页点全屏、再转竖屏会叠两层播放器）。
- **路线按来源各清各的**：`clearRouteWhileDesktop` 拆成 `clearPaneRouteWhileDesktop` / `clearDetailRouteWhileDesktop`。第一版一把全清，真机上"详情页停播再转竖屏"又掉回首页——右栏要先把宽度动画收完才离开组合，它 `onDispose` 时详情页那条路线刚被媒体库登记上，被顺手清掉之后媒体库再没有新的失效点把它登记回来。

### 验证（真机，逐帧）

- **播放中切竖屏**（`f6` 录屏 112-200 帧）：112 帧还是横屏"左列表 + 右栏画面"，120 帧起系统 3D 旋转开始，**128-168 帧整屏只有黑底 + 那一帧画面**，176 帧覆盖层淡出、184 帧起是竖屏播放页。修前同一条路径（`f2` 130 帧）是"竖屏播放页 + 首页/剧集页两层同时半透明叠在一起"。用户要的"切换动画是在播放界面的"成立。
- **详情页没在播切竖屏**（`g3`）：落在竖屏播放页、停在 41:01 未播放（中央是播放三角），不再掉回首页。
- **反方向**（`e1`）：竖屏未播放播放页 → 横屏 = 左栏剧集页 + 右栏画面，仍停在 38:46 未播放。

### 边界（不冒充已验）

- **系统转屏动画本身没关掉**：`ROTATION_ANIMATION_JUMPCUT` 在这台 HyperOS 上不被采纳，120-176 帧那段 3D 透视是系统在旋。现在旋的是"黑底 + 视频帧"这一张连贯的图，不再是两层页面；但动画时长与形状仍归系统，换一台 EMUI/ColorOS 或 AOSP 平板要重拍。
- 覆盖层时长受导航落位支配（实测 ~700ms，其中 ~570ms 是主线程转屏重排）。**没有去查那 570ms 里具体是哪棵树最贵**——要压它得先给媒体库那一屏做转屏期的重组裁剪，是另一件事。
- 覆盖层是顶对齐的 `Fit`，与播放页舞台的实际矩形不是逐像素重合，淡出时可能有几十像素的位移读成"轻微落位"。真机看着可接受，未做像素级对齐（要对齐就得把舞台几何在覆盖层再实现一遍，两份真相）。
- 只在**这台**平板拍过。手机横竖屏 `isDesktopLike` 恒 false，按源码不触发任何新分支，但未实拍；折叠屏、桌面自由窗口未拍。
- `play=0` 只挂在转屏交接这一条路径上。媒体库/迷你条/右栏 ⛶/深链全部保持"要播"。外部深链若自己带 `play=0` 也会生效——这是路由参数的自然结果，未额外设限。
- 真机测试期间把 `accelerometer_rotation` 置 0 以注入转屏，收尾已恢复 1；未改字号、密度与应用数据。临时打点已全部移除。

## E139 批 2：A1 的无样本可修那半（正片 AVI 不再被 32MB 拒），A6 未动

### 先说做不到的那半（这是本批最有价值的产出）

《任务文档》A1 的改法 1 与 2 在 media3 1.11 的**公开 API 上落不了地**，两条都是回源码/javadoc 核出来的：

- `ExtractorInput` 接口面上**没有** `skip` 也没有 `seek`（`seek(PositionHolder, long)` 只在 `DefaultExtractorInput` 这个实现类上）。所以"扫描用 skip/readFully 在同一次 read 里向前走"做不到：不返回 `RESULT_SEEK` 就只能把 payload 真读出来丢掉——两小时正片是**几 GB 的白读**，比原来的十几万次 seek 更糟。第一版照原文写了 `input.seek(...)`，编译直接 `Unresolved reference 'seek'`。
- `androidx.media3.datasource.DataSource` 接口只有 `addTransferListener / open / getUri / read / close`（javap 过 1.11.1 的 `classes.jar`）；`seek` 与 `canSeekAt` 在 `BaseDataSource` 上，而 `DefaultDataSource.Factory().createDataSource()` 的静态类型是 `DataSource`。所以"探测侧别每次 SEEK 都 close+open"也换不了——第一版写 `dataSource.canSeekAt(...)` 同样编译不过，已撤回。
- 结论：**"无 idx1 的 AVI 每块一次 SEEK，在 `content://` 上就是一次 `openAssetFileDescriptor`"这条风暴原样还在**。要断掉它，得给探测换一个可随机访问的输入（先把 uri 落成 fd / 缓存副本，再走 `FileDescriptorDataSource`），那是另一件事，仍记在 A1，不冒充已修。

### 那本批改了什么（A1 剩下的、确实能落地的）

`core:media` 新增纯函数面 `AviChunk`（fourcc 打包、流号/类型判定、`listEnd` 夹长、`pad`），解封装器改用它——**放纯模块是为了能在 JVM 上按字节测**：构造一个"声明 4GB 的 `movi` 头"只要 12 个字节，这条判定不受 B17 的素材欠账限制。

- **`LIST` 不再被 32MB 拒**：`readHeader` 原来在进 `movi` 分支之前就先 `if (size > MAX_CHUNK) throw`，正片的 `movi` 几乎全部在这里出局（探测 0 条 format → `Unplayable`；播放侧映射成"封装格式暂无解封装支持"）。现在上限只留给**真正按 size 分配内存**的地方（`hdrl` payload、`idx1`、样本），`LIST` 与只跳过的叶子 chunk 改为**夹到文件长度**（`AviChunk.listEnd`），OpenDML 写死的 `0xFFFFFFFF` 一并夹住。
- **每块都要付的三样开销拿掉**：`ckid` 从 `String` 改成 fourcc 打包 `Int`（两小时 25fps 是十几万个短命对象）；"这条流见过没有"从 `scanned.none { }` 的 O(n²) 比较改成 `MutableSet<Int>`；`materialize` 建完索引后清掉 `scanned`，不再两份一起驻留。
- **不再一遇异常就让整片出局**：扫描遇到截断（`EOFException`）、报不出长度的流式输入、或认出一个不可能的巨大样本块（解析跑偏）时，改为**用已认出的部分收尾**（`materialize` → `EMIT`），不再抛 `IOException`。
- **拖动不再谎报**：`isSeekable()` 现在只在关键帧信息可信（来自 `idx1` 的真 flags 位）时才可能为 true；扫描路径"每流第一块"是关键帧这件事是猜的，所以无 idx1 的文件**不再宣称可拖**。配套：`seek()` 在样本偏移单调时走二分（`idx1` 是解码顺序、不保证单调，所以单调性在 `materialize` 里算出来，不单调才退回线性扫）。

## E141 B21 阻塞诊断：MediaStore 对 app 整体隐藏非媒体文件；SAF 兜底打通判据①（并抓回自家一条 P0 回归）

### 探针轨迹（诊断，逐条可核）

```
sibling video=(1080p官方中字.mp4, Movies/)        ← 视频元数据拿得到
sibling sel=(_display_name = ? OR …) AND relative_path = ? / args=[1080p官方中字.ass, …] count=0
sub key=local:ms-1000008771 saved=null hit=null
sub toggle=true                                    ← 字幕总开关是**开**（候选①排除）
```

### 根因：MediaStore 按调用方权限过滤，`.ass` 对 app 不可见

- **同样语义的 SQL 经 `content query`（adb shell，特权身份）原样执行就命中**（等值、LIKE、加 `relative_path` 三种写法都试过），app 里恒 `count=0`。
- `dumpsys package`：`MANAGE_EXTERNAL_STORAGE: granted=false`，运行时只持有 `READ_MEDIA_VIDEO/AUDIO`。
- 结论：MediaProvider 对没有全盘权限的应用**把非媒体文件整体过滤掉**——`.ass`/`.vtt` 落成 `application/octet-stream`，不属于 app 可读的媒体集合。**与 LIKE 转义、与 SQL 写法都无关**（两种都跑过，都是 0 行）。
- 附带解释了一个长期现象：库是 SAF 扫出来的，而"同目录自动匹配"走 MediaStore——这条特性在真机上**从来没生效过**。

### 改法（落进代码）

1. **`resolveSiblingSubtitle` 重写**：MediaStore 一条保留（等值 + 显式括号），新增**已授权 SAF 树**一条并作为主力——把树的文档 id（`primary:Movies`）折成相对路径、与视频的 `relative_path` 比对，再用 `DocumentsContract` 列同级、按 ASS>SSA>SRT>VTT 取第一条，返回可被 app 读取的文档 uri。
2. **顺带修一处真缺陷**：旧的 `A OR B OR C OR D AND relative_path = ?` 里 **OR 比 AND 松**，前三条分支不带目录约束——别的目录里的同名 `.ass` 也会命中（可能挂错文件）。加括号后四条分支一律受目录约束。
3. 两个调用点（`SessionBootstrap` 新装载 / `PlaybackSession.restoreSubtitle` 切集重挂）把 `settings.scanFolderUris.first()` 传进来。

1. **两条 `pointerInput` 的 key 与当前值**：点按族改 `pointerInput(gesturesEnabled)`，动作统一从 `rememberUpdatedState(StageGestureCallbacks(...))` 读；拖动族 key 为 `(gestureActionsEnabled, deadZones)`，`gestureActionsEnabled = gesturesEnabled && !stageLocked`。锁定/设置里关手势后，双击快进、长按 3x 都读当前开关；单击唤出解锁钮的例外保留。
