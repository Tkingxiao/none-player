### 6.1 扫描与封面

- **[P2] 快照流式/Room 化**：当前快照 JSON 全量 `readText` 无大小限制；改流式或 Room，补大库峰值测量。
- **[P2] 设置组合流 + scanFolderUris 热快照**：启动就绪门；合并二三十条 map 流。
- **[P2] 失败项跨冷启 TTL**：封面失败已由 E203 的 `ScanCoverNegativeCache` 持久化（7 天/2000 条）；`ScanFailureMemo`（进程内 5 分钟）仍需覆盖嗅探/探测类失败项。
- **[P2] 增量扫描剩余项**：两条 MediaScanned 收一条；二三十条 map 流合流。（needsSniff 收窄、嗅探并发、分阶段进度与取消已由 E201 完成）
- **[P2] 增量索引的陈旧窗口**：叶子目录内**同名覆盖写**（`cp` 覆盖、`touch`）不改父目录 mtime，`ScanWalkIndex` 5 分钟 TTL 内仍显示旧 size/mime。要更快收敛需 TTL 内复检或 `FileObserver`。
- **[P3] 封面泵并发上限未接车道预设**：`CoverPump` 的 worker 数与许可上限固定为 `decodeWorkers()`（8 核机 = 4），不读 `scan_lanes.json` 里 E202 调好的 COVER 预设，真机抽帧 6.9ms/项 vs 扫描内 8 许可的 5.75ms/项；且 `ScanLaneTuner` 只按成功项计吞吐，坏文件多的库（全失败）恒 `target=idle` 不爬坡。
- **[P3] 急滚预备缓存只有定性验证**：`CoverWindow` 覆盖「可见 ±1 屏 + 急滚方向 2 屏」，真机只验证了单屏 6 项与一次 `demand n=6`，未做大库多屏快速滚动丢帧/占位统计。
- **[P3] 车道调参的负载突变误判**：`ScanLaneTuner` 按窗口吞吐判膝点，若后段目录/文件明显比前段重（walk 常见），吞吐下降会被判成竞争饱和并回落锁死（真机 COLD1 里 WALK 从 18 落回 15）。要更准需按「已完成项目的耗时分布」归一化，而不是原始项目数/秒。
- **[P3] 大核识别兜底**：`ScanCpuTopology.splitBigCores` 依赖逐核 `cpufreq/cpuinfo_max_freq`，部分机型/内核该节点不可读时 `bigCores` 会退化成 1（真机 SM8250 即报 `big=1`），解码型初始许可因此偏低，靠 tuner 爬坡补偿；可加「读不到频点就按 4 大核/8 核比例估」的兜底。
- **[P3] 车道预设与库规模无关**：`scan_lanes.json` 只按车道种类记许可，换设备/换目录/库规模量级变化后仍沿用旧值，需要一个规模或耗时变化触发的重试条件。
- **[P2] 审查收口余项（媒体库）**：contentType 收益量化、扫描器侧封面、富化/嗅探耗时测量。
